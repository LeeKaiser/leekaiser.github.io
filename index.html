Hero Shooter Maker

Unity, C# · Personal & Capstone project

A template codebase for combat focused games. Recreating systems commonly seen in some of my favorite videogames. Includes 9 different major mechanics, such as Characters, Bots, Abilities, Teams, etc.

Major Features

  • Character system: manages interaction between characters.
  • Ability system: flexible, event-activated ability system that can be added to characters, applicable for making a wide variety of abilities from hero shooters.
  • Status effect system: flexible status effect system with duration controls.
  • Character AI: makes the character operate without player input, to simulate matches or to use for minion-type characters.
  • Match systems: scripts to support teams and game mode objectives.
  • Projectiles: consistent and flexible projectile system that can be used to make a wide variety of attacks.
Design Decisions & Implementation Process

Input

The input is decoupled from the character. This allows both the agent and the player to control the character without disparity in what they are able to do. The input from a player simply invokes an event, and any ability whose activation method is subscribed to that event is then called. The agent can also invoke the same event. I decided to implement it this way because in my favorite game, Brawl Stars, there are occasional instances of very long lasting bugs where the bots did not use their abilities correctly, and I did not want to make the same mistake. The easiest example is a bot playing as Gigi, where the bot is not able to attack as Gigi and is effectively a sitting duck. (I speculate that Gigi suffers from this bug because her attack has a unique property where the attack rate increases as her remaining ammo decreases, but the true reason is not confirmed by anyone.)

The input is represented by a scriptable object, which contains information about the combination of keys the user pressed, and three types of key presses: press, hold, and release, as well as priority in case one type of input needs to override another.

Event Activated Abilities

The systems in Hero Shooter Maker are designed with the intention that abilities activate from events. It is designed this way because it makes it easy to add on Active abilities that activate from input associated events, as well as passive abilities that activate from in-game events like the player taking damage or being airborne.

Actions Made from 3 Different “Determine” Classes

The agent’s actions use a strategy pattern, building their behavior through 3 different “Determine” classes. The first determines where they decide to move. The second determines where (or who) they decide to aim at, and the third determines what ability to use. I realized these three strategies were enough to create an agent behavior for a character in a hero shooter.

This design was inspired by Brawl Stars’s development history. Brawl Stars currently has the player control their character through dragging a blue joystick. But when Brawl Stars was in early beta, they used a tap to move system (like League of Legends and other MOBA games). The visual indicator showed a large white circle at the character’s destination. Interestingly, that circle is still present in the game to this day, which appears on the character’s movement direction when dragging the blue joystick. This gave me the idea that the pathfinding algorithm could be converted to input that would trace that path at a given moment. I created a movement script that makes the agent input the correct movement keys to reach their destination, a surprisingly difficult task when trying to make them successful at platforming in a 3D environment as well.

I wanted the agent to be able to reach any location that a normal player would be able to reach. So I invested time into perfecting its movement input to correctly perform platforming. When an agent reaches an “off mesh link” that is positioned at a ledge or right before a platform, it assesses if the movement to the other side will require a jump using the function:

y > ½ · g · (x / s)2

where y is the vertical distance, g is gravity, x is the horizontal distance, and s is the agent’s speed. The agent’s movement input actively moves towards the landing location, ensuring that it lands on the platform at the intended location instead of missing it and flying off somewhere else.

The aiming system was similarly inspired by Brawl Stars. When Brawl Stars changed their movement system, they also added a feature where attack and other abilities can now be “Auto aimed” by tapping on the joystick instead of dragging it across the screen. The Auto Aim simply targets the nearest enemy. I thought that if I had this simple targeting algorithm, and also had other targeting options like aiming at the lowest hp remaining or farthest target, it could allow the agent to target strategically based on the situation.

Decision Tree Logic

The agents decide what they should do using a decision tree. I was struggling with how I should create the decision making logic. I wanted something that I could build within a few weeks to scope for my Capstone timeline, a design that was easy to work with for designers, and a logic system that could take multiple factors into account, using the object detection system. The expert that I was consulting taught me about decision trees. When thinking about what they taught me, I realized that the structure of decision trees closely matches binary trees. I began with a binary tree, then diverged from that original design by making improvements such as allowing a node to have multiple parents to make it so multiple conditions can lead to the same action to avoid the need to create duplicate actions. Using a custom editor for creating and editing the decision tree, it is very easy to create a custom logic for how the agent should behave.

Object Detection Optimizations

I started with an object detection logic I learned from a tutorial in high school. Using OverlapSphere to detect all objects within a radius, and filter out objects that were not in its field of view if necessary. I decided to optimize it from the start by having the object detection method be called every set interval rather than every frame, so that it is not running for the majority of the runtime. This logic functioned well for the intended use case of 5 to 10 agents in average situations and maximum of about 30 concurrent agents, but my friend from the Capstone class recommended I stress test it by having many concurrent agents. Unity slowed down to a crawl and crashed when I put hundreds of concurrent agents in my test map. So I decided to make a scene dedicated to testing agent performance, with large groups of agents, each doubling in numbers, that I can easily enable and disable. I then checked the Unity Profiler, which showed the processes that were running with each frame. I noticed that there were many processes that were each used by an agent, which activated every set interval.

I realized that when agents were near each other, the object detection logic was O(n²), with n being the number of concurrent agents in the same area. Each new agent needed to detect all existing agents, and all existing agents also needed to detect the new one, so the computational load grew quadratically. Since each agent’s detection didn’t depend on any other agent’s results, the work could run in parallel. I looked into the Unity Jobs system and moved object detection onto worker threads and batched the physics queries. This increased the performance from ~2.9 fps to ~46.7 fps with 128 concurrent agents (Apple M4 Pro), a ~16x improvement.

I then had a thought. Hero shooters usually have a PvE mode, where there can be many agents at once, an iconic example being Team Fortress 2’s Mann vs Machine, and there are even games that are dedicated to hero based character systems with PvE gameplay like Deep Rock Galactic. The agents in those games do not need to collect as much information as the agents replacing a player, so I could implement an alternative detection system for cases with hundreds of simpler agents. I implemented an alternative detection system where, instead of the agent “seeing” relevant objects, the relevant objects (like the player or key locations) “revealed” themselves by adding themselves to the agent’s detection list. This flips detection from the agent searching for objects to a small number of objects announcing themselves to the agents. Because only a few objects reveal themselves, the cost scales linearly with the number of agents, at the cost of agents not being able to detect anything that isn’t revealing itself. I was able to run 512 concurrent agents at ~30 fps (Apple M4 Pro). The method for revealing self to other agents also uses multithreading.

Projectile System

I created a custom projectile system, which is modular with many useful components. One of the most useful features of this projectile system is that the projectiles can be grouped together to create more complex attacks. Each projectile has a “ProjectileInfo” component, which stores key information like the objects the projectiles collided with on a given fixed update. If the projectile is part of a group, this info is also sent to the group’s ProjectileInfo. Other components of the projectile source collision information from the ProjectileInfo to then apply their function such as dealing damage or applying a status effect.

I used a SphereCast to find all objects between where the projectile is and where the projectile will be in the next Fixed Update. This allows the projectile to collide with objects much more consistently than simply detecting collision with a collider.

Future Work

The major features I wanted to add are complete, and it can be used as a package by downloading it from my GitHub. But there are still a few tasks I want to work on to improve the project.

  • Bug fixes, additional testing, and polish: I’m fixing a few remaining bugs to ensure the project functions as intended. I’m also looking into adding warnings when the developers do not use the features correctly (such as forgetting the character’s stats object) to help them avoid bugs.
  • Documentation: I’m writing more comprehensive documentation so other developers can pick up the project easily.
  • Projectile system expansion: I want to create unique projectile travel patterns such as homing and orbiting projectiles, a “hitscan” attack that only uses SphereCast once to instantly hit a target, and implement damage falloff on the ApplyDamage component.
  • Release on the Unity Asset Store: Once the documentation and bug fixes are complete, I want to release this project on the Unity Asset Store, to reach other developers who could benefit from this project.
